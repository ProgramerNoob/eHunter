# 迁移 Spec Kit 规范与工作流到 Trellis

## Goal

让 Trellis 成为 eHunter 唯一的开发工作流与规范入口，在删除旧框架前保全产品目标、功能契约、有效决策、验收流程和未完成工作。

## Background

- 用户要求删除根目录 `specs/`、`design.md`、`.specify/`、`.pi/prompts/` 中的 speckit 文件、`.pi/browser-testing.md`、`.pi/speckit-maintenance.md`，并更新 `AGENTS.md`。
- 用户已审阅最终规划并选择“按方案执行”；任务已激活，按保全、退役、检查、审查的顺序实施。
- 工作区基线为 `647ff26`。只读审计确认现有 Trellis 工程指南没有完整承接产品资料；待处理来源共 115 个受版本控制文件，其中 `specs/` 为 57 个。
- 七组 tasks 共 366 条，252 已勾、114 未勾；requirements checklist 为 124 条/12 未勾，quickstart 为 24 条/24 未勾。计数、来源定位及差异说明见 `research/migration-audit.md`，逐文件基线见 `research/source-inventory.json`。

## Requirements

1. **R1 知识保全**：每份旧资料有可追溯去向；完整保留产品目标、七组功能需求、数据模型、契约、已确认决策、验收步骤和历史证据。
2. **R2 状态准确**：保留任务编号、原勾选、未完成事项及不同清单的独立状态，使后续开发可从 Trellis 找到。必须区分目标、现有代码和实际验收；尤其保留平台 T043–T082/T098 的陈旧清单说明、T149 未修状态、60 秒契约与 120000ms 实现差异，以及翻页/设置旧勾选免责声明。来源证据集中在审计的“必须保留的状态差异”段。
3. **R3 工具退役**：移除用户指定的旧路径与 Spec Kit 专用工具；稳定工程原则保留，Spec Kit 命令/模板/hooks/治理退出当前工作流。
4. **R4 验收能力与引用**：完整保留浏览器操作、服务归属/清理和 EH 生产包验收能力；更新 AGENTS、Trellis 指南、保留技能、README 与发布排除规则中的有效依赖。本机配置仅移除已失效的 Spec Kit prompt 项，其他内容保留且不纳入版本控制。
5. **R5 实现边界**：本次仅迁移文档与开发工作流；保留 Trellis 托管区/通用资产，产品源码、依赖、构建配置和用户可见行为不变。

## Acceptance Criteria

- [x] **AC1 → R1/R3**：115 个受版本控制来源均有处理记录；59 个完整迁入文档可追溯，constitution/maintenance 的稳定规则有条款映射和退役理由。
- [x] **AC2 → R1/R2**：所有有效知识和未完成事项可从 Trellis 索引找到；需求、契约、任务 ID/状态、历史验收记录保全，已知冲突和决策优先级清楚。
- [x] **AC3 → R3**：用户指定的旧路径及 15 个 Spec Kit prompts 均已移除，保留工具可正常发现。
- [x] **AC4 → R4/R5**：AGENTS、Trellis 工程指南、README 和保留技能无指向已删除文件的有效依赖；本机设置仅清理约定项；产品与 Trellis 托管资产未改动。
- [x] **AC5 → R1–R5**：文档引用/锚点、格式、命令路径、迁移保全、任务上下文和发布排除检查通过；固定版本独立审查无阻塞项。
- [x] **AC6 → R5**：交付明确已验证范围，以及未运行的产品构建、类型检查和浏览器功能验收。

## Out of Scope

- 不修复或完成历史任务中的产品缺陷，也不依据未勾清单重新实现已有代码。
- 不批量创建历史功能任务；保留可发现的待办入口，实际开展时按 Trellis 规划。
- 不升级 Trellis、不改写通用模板工作流、不重构产品源码、不恢复 Spec Kit 自动上下文维护机制。
