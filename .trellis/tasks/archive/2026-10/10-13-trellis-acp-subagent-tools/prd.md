# 恢复 Trellis 子代理的 ACP 压缩能力

## 目标
使 Trellis 子代理在现有工具限制和 --no-session 启动方式下能主动压缩上下文，并继续完成任务。

## 背景
属于 [总任务](../10-13-trellis-acp-context/prd.md) 的 R1、R3、R4。
本轮已确认 agent frontmatter 未包含 ACP 工具，buildPiArgs 原样传递该白名单。历史运行期结论和当前配置差异见 [核查记录](../10-13-trellis-acp-context/research/baseline.md)。
工具缺失的运行机制与最小修复路径仍需真实子进程验证；不能从白名单文本直接报告运行验收通过。

## 需求
- 保留 trellis-implement、trellis-check、trellis-research 各自现有业务工具限制。
- 分别识别扩展加载失败、白名单过滤、无可压缩范围和压缩请求失败。
- 将工具可见性验证与实际压缩验证分开记录；运行结果能归属到具体子会话。
- 优先采用项目内最小改动；全局安装包补丁与上游发布不在本任务范围。
- 不将 pi.subagents 开关视为第三方 Trellis spawner 的修复依据。

## 接受标准
- [AC1] 在与 Trellis 一致的 --mode json -p --no-session 子进程中，记录修复前后工具暴露情况，三个角色能获得所需 ACP 工具且保留现有业务工具限制。
- [AC2] 真实子进程中存在可压缩范围时，模型主动调用 compress 成功；记录调用与结果，并在压缩后正确使用预先放入的任务事实。
- [AC3] 通过真实 trellis_subagent 派发完成一个有明确交付物的代表性任务，输出可验证结果，并将角色覆盖范围、耗时、失败情况和回滚方式写入交付记录。

## 依赖与边界
可独立验证和交付。尚未证明子代理具备 ACP 能力前，由主会话负责最小复现，避免让待修复链路承担自证。
本任务不负责调整 nudge 策略或证明长期缓存收益。用户已限定为项目内修复，保留用户级 ACP 配置、全局 Pi 设置和安装包；若项目内路径受阻，记录原因与未验证范围。
